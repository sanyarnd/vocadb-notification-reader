# CrowdSec

Scenarios that ban clients brute forcing VocaDB credentials or ignoring rate limits of the
backend. They work on the access log of the reverse proxy, the backend itself doesn't need
to be known to CrowdSec:

| Scenario                                  | Triggers on                                                                      |
|-------------------------------------------|----------------------------------------------------------------------------------|
| `vocadb-notification-reader/login-bf`     | 10 failed logins (`POST /api/session` answered with 401 or 429) in quick succession, one failure is forgiven per minute |
| `vocadb-notification-reader/rate-limit`   | 30 requests to `/api/` rejected with 429 in a burst, one is forgiven every 10 seconds |

The scenarios rely on the `http_access-log` events of the `crowdsecurity/caddy` collection
(any other HTTP access log parser providing `http_verb`, `http_path` and `http_status` works too).
The API host must be logged to a file CrowdSec reads, with the real client address.

## Installation

```shell
cscli collections install crowdsecurity/caddy
cp scenarios/*.yaml /etc/crowdsec/scenarios/
```

One address may be shared by many people (NAT), so [profiles.yaml](profiles.yaml) shortens
the bans to an hour.
Put its document before `default_ip_remediation` in `/etc/crowdsec/profiles.yaml`.

Then reload CrowdSec (`systemctl reload crowdsec` or restart the container) and check:

```shell
cscli scenarios list | grep vocadb-notification-reader
cscli explain --file /path/to/access.log --type caddy   # which scenarios a log line reaches
```

## Tests

`tests/cases/` contains Caddy access logs (generated by `tests/generate.py`) with the scenarios
each of them must trigger. `tests/run.sh` replays them through CrowdSec and also checks that the
profile turns an alert into a one hour ban:

```shell
docker run --rm -v "$PWD:/vnr:ro" --entrypoint /vnr/tests/run.sh crowdsecurity/crowdsec:v1.8.1
```
